# 第二份 Soot PR：既有接口接入验证

2026-10-28。本轮只做隔离实验，没有推送或回复上游。

## 结论

在本轮已测配置下，Soot 既有接口可以绕过两个新工厂，完成 92 项当前引擎 XML 回调集成测试；其中 12 项再次运行并增加状态观察。这个结果不证明已有接口组合是通用的替代方案，也不能单独决定工厂是否需要保留。

但当前替代适配器不能完整取代 `processNewMethod()`：通过 MethodSource 准备摘要依赖方法体的加载时机，独立生成的 active body 会绕过它。已有明确失败样本，因此不将这个实验作为最终接入方案。92 项通过只说明已测场景的结果，不能证明机制通用。

第二份上游 PR 的摘要消费与传播应复用原有构图器工厂和 `processNewMethod()`。要在实际引擎中通用接入，仍必须解决标准 `cg.spark` 固定创建链如何使用客户端构图器的问题；这不是可以忽略的需求。本轮交付是调查结论及设计约束，尚未完成正式接入方案，也没有决定工厂接口的最终形式。

## 通用设计的判断标准

用户明确要求最终方案具有通用性。最终设计应满足以下不变量，而不是按当前样例添加处理分支：

1. **处理时机统一。** 方法首次可达并通过已有分析范围判断后，在分析其调用之前准备摘要。预加载、懒加载和直接合成的方法体使用同一路径，不依赖来源包装或新增 body 的生成方式。已有 `OnFlyCallGraphBuilder.processNewMethod()` 正好位于这个生命周期位置。`processReachables()` 的范围守卫在调用它之前执行；本轮未修改守卫，也未额外运行 apponly 模式矩阵。
2. **职责分开。** 客户端解释 XML 并匹配具体调用点；Soot 消费通用的调用点摘要，不加入 Handler、Executor 或某个项目专用的识别分支。新增符合协议的 API 模型不要求修改 Soot 核心。
3. **协议一致。** CG 建立的回调目标与 PAG 的 receiver/参数映射来自同一摘要；普通调用目标和原有分类保留。支持的目标及映射形状应明确，未支持的形状不能悄悄丢失语义。
4. **生命周期局部。** 客户端匹配状态随本次构图实例管理，不保存在 Scene 全局监听器中，不靠构图后的补边或第二次建图修正之前的传播。
5. **组装接口最小。** 复用现有构图器工厂和上述处理入口。若标准 SPARK 的固定创建链阻止实际客户端接入，再针对对象组装边界讨论最小扩展。两个新工厂只负责创建对象，不应成为两处模型准备逻辑；其必要性和提交范围需要独立说明。

现有调用点摘要协议限定为 GENERIC_FAKE、一个 DirectTarget 和直接引用参数映射，可按 base 或参数选择回调对象；局部摘要覆盖该语句的默认摘要，null 明确抑制默认摘要，其他语句不受影响。边类型和目标形状在构造时拒绝不支持形式，非直接映射在 PAG 消费时拒绝；非法索引等输入不属于本轮已验证范围。这里的通用性指协议与具体 API 解耦，不宣称已支持所有摘要形状。

方法体在进入分析后应保持稳定。若之后替换、重写或重新加载，必须遵循 Soot 的失效和重新构图机制；本轮没有实现任意修改后的摘要版本管理，也不承诺支持这种运行方式。

因此，已有接口实验回答了“能否在一些实际场景实现功能”；上述不变量才决定正式方案。MethodSource 包装和传播阶段换图都不能以本轮通过为由当作通用方案。后生成方法体反例是本轮的明确排除证据。

## 目标与范围

目标是让实际 XML 匹配产生的调用点摘要正确进入 CG、SPARK 和后续 IFDS，保留普通调用目标、库归属、回调对象及参数关系。工厂、provider 和 MethodSource 包装都是接入手段。本轮没有扫描性能实验，也没有迁移第一份权限策略。

## 已有接口方案

1. 构图前处理已存在的 active body，包括有限模型方法体。
2. 通过已有 `SootMethod.getSource/setSource` 包装未加载方法，委托原来源创建方法体，再执行真实 XML 匹配。
3. 在来源委托返回后检查新生成的方法，捕获本轮 lambda 场景。
4. 继续执行原有 `cg.spark` 和 IFDS，不注册全局 provider，不使用两个新工厂。

该方案安装了 115 个冷方法来源包装，但每个选定场景只委托加载 3–7 个。初始准备 49 个已有方法体，lambda 场景为 52 个。它不是“只对新可达方法执行一次”的同一生命周期；其刷新遍历成本及所有动态创建方式没有全面验证。

## 上游机制与边界探针

上游探针以官方 `2685932cb87821e41423389078ccfadb9af947ee` 的 `SparkTransformer` 和 `ContextInsensitiveBuilder` 源码编译覆盖层，并反射排除两个新方法。主审独立重编译、重跑已有体和冷方法两个模式，均通过嵌套回调、this/参数 points-to、后续虚调用、普通 API 边和其他调用隔离断言。

覆盖层以外的摘要实现来自 `084b232569326725433ef9831c730df5e6f3a77b` 已编译产物，不是完整原版基线。`runtime-bytecode-binding.json` 记录覆盖层、主类、测试类全部 class 和依赖 JAR 的 SHA256；重现时先构建该提交，再编译官方两类覆盖层。两者的来源和作用不可混称。

以下边界均实际执行：

- 向 `jb` 追加任意 Transform 不会执行，因为 JimpleBodyPack 按固定阶段名调度。
- `retrieveActiveBody(consumer)` 对已有 active body 不调用 consumer；`setActiveBody` 也不走来源加载流程。
- 初版简化来源包装探针没有完整刷新逻辑，仅说明其自身边界，不单独用于判断完整候选。
- 随后用相同的“来源委托＋完整刷新”机制复核：安装后独立创建 `LateBridge.forward` 的 active body 并从入口调用。没有后续冷加载时，方法可达但摘要未准备；有冷加载刷新时，摘要最终已准备，但其回调边仍缺失，因为该方法的调用扫描已经完成。三种模式使用同一条“可达合同必须产生回调边”断言；两个包装模式均失败，处理入口对照通过。

最后一个样本是受控方法体边界，复用了完整刷新机制但没有执行真实 XML 匹配器，不宣称某个真实模块已发生同样漏报。它证明来源刷新时机与新可达方法处理入口不同：事后补上摘要也不能自动重扫已经处理过的调用。成功对照使用传播阶段重建图，只证明这次 processNewMethod 调用看到了该方法，不验证正式首次构图的注入设计。

另一已有 `propagatePAG` 扩展点也能让受控样例通过，但需要在初次构图之后替换调用图。旧 PAG 约束和 MethodPAG 缓存仍在，不能靠换图撤销。本轮不推荐把这种重建技巧作为生产方案。
